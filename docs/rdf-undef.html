rdf-undef extends the data model of rdf-array.md with one thing: a position in a sequence may be empty.

This is a working document of the rdf-array project, generated from docs/rdf-undef.md by tools/md-to-respec.py in the same repository. It is not a W3C document and has no standing anywhere.

Introduction

Design note, 2026-11-01, on the rdf-undef branch of the repositories, which branches from rdf-sequences. Prototyped in jena-array (the tests in TestUndefSlots), owlapi-array (UndefReasoningTestCase) and protege-owl-array (the roster walk-through), each on its branch rdf-undef. This is a strawman: §6 lists the decisions that are still open.

:x :p ( 1 undef 3 ) .

That sequence has three positions and nothing at the second. The marker is undef, the word SPARQL already uses for "no value here" in VALUES.

What a slot is

A slot is a position with no value. Three consequences carry through everything below:

  • It is not a term. undef occurs only as a member of a sequence, at any depth. :s :p undef and undef :p 1 are syntax errors, in Turtle, N-Triples and SPARQL alike. A variable is never bound to it.
  • It is not an unknown value. ( 1 _:b 3 ) already says "there is something at the second position and I am not saying what". undef says there is nothing there, so ( 1 2 3 ) does not entail ( 1 undef 3 ), nor the reverse. This follows from owl-array.md §3.1, "a sequence is closed".
  • It counts. ( 1 undef 3 ) has length 3. Two sequences are the same term when their members and their slots line up: ( 1 undef ) is ( 1 undef ), and is different from ( 1 ), ( undef 1 ) and ( 1 2 ).

Syntax

Turtle, TriG, N-Triples and N-Quads take undef as a sequence member, in any case, as SPARQL does. Writers emit undef. A prefix may still be called undef:, since the tokenizer reads undef:x as a prefixed name.

SPARQL takes it as a member of a sequence in patterns, templates and data blocks, and as an argument of SEQ: ( ?a undef ?c ), SEQ(1, undef, 3). It is not an expression elsewhere, so BIND(undef AS ?x) is a syntax error. VALUES ?x { undef } keeps its meaning.

Result formats reuse their own word for no value: { "type": "undef" } as a member of a JSON seq, and <unbound/> as a child of an XML <seq>. SSE writes (seqterm 1 undef 3).

SPARQL

The rule for variables comes from VALUES: UNDEF there leaves a variable unbound, and an unbound variable joins with anything. A slot does the same. Over :x :p ( 1 undef 3 ) and :y :p ( 1 2 3 ):

Query partResult
?s :p ( ?a ?b ?c )at :x, ?a is 1, ?c is 3 and ?b is unbound; at :y, all three are bound
?s :p ( ?a undef ?c )only :x: undef in a pattern matches only a slot
?s :p ( 1 2 3 )only :y: a constant does not match a slot
?s :p ( ?a ?b )nothing: the length still has to match
VALUES ?b { 5 } ?s :p ( ?a ?b ?c ):x with ?b 5, joined as with any unbound variable; not :y, which has 2

:x :p ( ?h ...?t )?t is ( undef 3 ): a named gap keeps slots
UNNEST(?s AS ?m AT ?i)three solutions; at ?i 2, ?m is unbound; FILTER(BOUND(?m)) drops it
?s[2]an error, as out of range is, so BIND leaves its variable unbound and COALESCE(?s[2], 0) gives a default
?s[2...3]( undef 3 ): slices keep slots

Bottom-up evaluation has to give the same answer as an engine that substitutes bindings into a pattern, and two things in Jena had to change for that:

  • A variable bound earlier is compatible with a slot, yet a written constant must not match one. So the matcher works from the pattern before substitution, and a sequence pattern is not looked up in the graph by its substituted form.
  • A variable inside a sequence pattern is no longer certain to be bound. The optimizer's analyses (VarFinder, OpVars.fixedVars) now count those variables as optional, and so the UNNEST variable too, so that joins and filter placement stay correct. Queries without slots return the same answers, though some joins may now use a less specialised strategy.

OWL

Implemented in owlapi-array and run in Protégé on 2026-11-02 (§4.1). The point of writing the plan before the code was to check that §1 and §3 leave it possible; §4.2 has what the reasoner then found.

The direct semantics of owl-array.md §3.1 gives sequences as tuples of denotations. rdf-undef adds one thing to what a tuple's element may be, a distinguished hole, which is not in the object or data domain:

  • Denotation. ( t1 … undef … tn ) denotes the tuple with a hole at that position. A hole denotes itself in every interpretation.
  • Identity. Still by elements, pairwise, with a hole equal only to a hole. So ( 1 undef ) owl:differentFrom ( 1 2 ) holds in every interpretation, and owl:sameAs between members never reaches a hole.
  • Closure. A sequence stays closed, and later data cannot fill a hole.

The built-ins of owl-array.md §3.2 need no change of meaning, since each is already stated over elements that are individuals or values:

TermAt a hole
ra:lengthcounts it: ( 1 undef 3 ) ra:length 3
ra:member, ra:memberValueno assertion, so ra:member only C holds vacuously at a hole, as it already does at a literal (§3.5)
ra:first, ra:last and the Value formsno value when the first or last position is a hole; they are already partial

One addition is needed, because ra:member only C can no longer say "every position holds a C":

New termKindMeaning
ra:holesfunctional data propertythe number of holes of s, an xsd:nonNegativeInteger
ra:DenseSequencedefined classra:Sequence and ra:holes value 0

Entailments, given ex:r ex:rgb ( 255 undef 0 ):

  • ( 255 undef 0 ) ra:length 3 and ra:holes 1;
  • ( 255 undef 0 ) ra:memberValue 255, and ra:memberValue 0;
  • ( 255 undef 0 ) a ra:DataSequence, and not ra:DenseSequence;
  • with ex:r a ex:Swatch, a class requiring ex:rgb only (ra:length value 3 and ra:memberValue only xsd:integer), the ontology stays consistent; adding ra:DenseSequence to that requirement makes it inconsistent;
  • ( undef ) a ra:ObjectSequence and ra:DataSequence, vacuously, and not ra:EmptySequence, since its length is 1;
  • ex:r ex:rgb ( 255 7 0 ) is not entailed, for any value in place of the 7.

The expansion of owl-array.md §6 stays linear and stays within OWL 2 DL: it emits no member assertion for a hole, it counts holes for ra:length and ra:holes, it spells undef in the canonical IRI so that equal terms keep one individual, and the HasKey axioms per length (still not implemented) would apply per pattern of holes, since sequences with holes in different places are different.

As implemented

owlapi-array, branch rdf-undef (its doc/rdf-array.md has the detail): OWLUndef is an element of an OWLSequence and nothing else, one object, spelled undef in the node ID; the Turtle parser and writer take it, RDF/XML refuses it as it refuses a literal element, and a slot in one of OWL's own lists is a parse error. SequenceAxioms expands as above, plus one thing the plan missed: with the closure, an end that is a hole gets ra:first max 0 and ra:firstValue max 0 (or last). The vocabulary (vocab/owl-array.ttl on this branch) gains ra:holes and ra:DenseSequence, and its axiom "a non-empty sequence has a first and a last" is restated for dense sequences. Protégé runs it through protege-owl-array's bundle; protege-undef.md walks through the roster example, a week's shifts with days off as slots.

What the reasoner found

Each is a test in UndefReasoningTestCase, against HermiT.

  • The phantom first. ( undef 2 3 ) has no first. The vocabulary said that a non-empty sequence has a first or a first value, and the closure said the values are 2 and 3, so HermiT concluded ra:firstValue some {2, 3}; and ( undef ), non-empty with no members, was inconsistent. Two changes: the axiom now speaks of ra:DenseSequence and not ra:EmptySequence, and the expansion says of a hole at an end that there is no first (last). ra:first over ( undef 2 3 ) is then undefined, ra:last is 3, and ra:first max 0 holds: "Monday off" is ra:first max 0 and not ra:EmptySequence.
  • "No members" no longer means empty. ( undef ) is ra:member max 0 and ra:memberValue max 0, not ra:EmptySequence (length 1), and vacuously both ra:ObjectSequence and ra:DataSequence, as () is. An ontology that defined emptiness by the absence of members now admits every all-slot sequence; ra:EmptySequence is defined by length and is unchanged.
  • ra:member counts members, ra:length positions. ( ex:a undef ex:b ) with ex:a and ex:b different is ra:member exactly 2 and ra:length value 3. "Every position holds a C" is now three conjuncts: ra:DenseSequence and ra:ObjectSequence and ra:member only C.
  • only is vacuous at a slot. ra:memberValue only xsd:integer[<= 8] holds of a sequence of slots, so "short days only" lists a worker on leave; ra:member only :Shift holds of a week of days off but not of a week holding a blank node, which is the difference between a slot and an unknown made visible.
  • Which sequences the expansion tells apart. ( 1 undef ) owl:differentFrom ( 1 2 ) follows from ra:holes being functional, ( 1 undef ) owl:differentFrom ( undef 1 ) and ( undef 2 3 ) owl:differentFrom ( 2 undef 3 ) from the end closure. ( 1 undef 2 3 ) and ( 1 2 undef 3 ) are not told apart, as ( 1 2 3 4 ) and ( 1 3 2 4 ) were not before: the expansion is sound and incomplete for owl:differentFrom, and the inner positions are what it cannot see. Positional properties, if ever added, would close this; a slot is simply a position without a value for them.
  • Holes are not counted through nesting. ( ( undef ) ) is ra:DenseSequence and ra:member some (ra:holes value 1). Depth-two density is ra:member only ra:DenseSequence.
  • A sequence with a slot is a nominal like any. ex:Holey EquivalentTo: ex:rgb value ( 1 undef ) classifies the individuals with that value, and ( 1 undef ) written twice is one individual.
  • OWL 2 EL (closure off). ra:DenseSequence is ra:holes value 0, which EL has, and functional data properties are in EL too, so density and sparseness are decided without the closure; only and max 0 still need it. (Moving the functional data properties out of the closure-only set also cured a HermiT oddity: its first isEntailed about ra:DenseSequence, before any realisation, answered false.)
  • A slot in one of OWL's own lists (owl:unionOf ( ex:A undef )) is an error, not an empty union: the lax reading of a non-list hid it.
  • Found on the way: owlapi-array's reasoner decorator expanded a sequence named only by a query once and then forgot it had not, so a second isEntailed naming the same foreign sequence answered over an individual with no axioms. Fixed on both rdf-sequences and rdf-undef.

How the SPARQL semantics keeps this open

Choice in §1 and §3What it preserves
A slot is never a term and a variable never binds itOWL needs no individual for it, and ra:member needs no exception
A constant does not match a slotAn entailment regime stays sound: ( 1 2 3 ) is not entailed by ( 1 undef 3 ), and SPARQL does not claim it
= is false between a slot and a valueThe same answer as owl:differentFrom
IN skips slotsThe same answer as ra:member and ra:memberValue
Length counts slotsThe same answer as ra:length
undef matches only a slot, by term( 1 undef ) owl:sameAs ( 1 undef ) is simple identity

The one thing that would have to change is the reading of undef itself. If it meant "unknown", then ( 1 undef ) = ( 1 2 ) would be an error and not false, 2 IN ( 1 undef ) likewise, and a sequence with a slot would be anonymous under owl-array.md §3.1, barred from owl:hasValue and owl:oneOf. Those are few changes in code, but the OWL semantics would need an existential reading, which ( 1 _:b ) already gives. That is the case against it.

The implementations agree on every row of §3's table and on the contrib tests. What this turned up:

  • VALUES holds no sequences, with or without a slot, in Jena and Oxigraph, so §2's "data blocks" is reached only by INSERT DATA and DELETE DATA.
  • CSV differs, as it did before slots. Jena writes ? for any sequence, and Comunica and Oxigraph write it out, so the suite has no slot case for CSV.
  • JSON-LD implementations differ where neither is a slot. An array directly in @list, {"@list": [[1]]}, nests in jsonld.js, the streaming parser and rdflib and flattens in Oxigraph; {"@list": null} gives an empty node in jsonld.js and rdflib and no triple in the streaming parser. Neither is in the suite.
  • N3 does not read undef in Oxigraph, since this note names Turtle, TriG, N-Triples and N-Quads.

Open decisions

  1. A variable at a slot stays unbound. The alternative is that ( ?a ?b ?c ) does not match ( 1 undef 3 ), and only undef or a gap reaches past a slot. That keeps "a pattern binds all its variables", which the optimizer relies on, and it is simpler; but it treats UNNEST and [i] differently, and it hides the data from a query that does not expect slots.
  2. A variable bound elsewhere joins through a slot. VALUES ?b { 5 } ?s :p ( ?a ?b ?c ) returns :x with ?b 5, though :x has no 5. This follows from the join and from VALUES, and it may still surprise.
  3. ( ... ?m ... ) and UNNEST give a solution at a slot. The alternative, like JavaScript's forEach, skips slots; UNNEST would then still have to number the rest by position.
  4. An unbound variable in a template's sequence writes a slot. It makes CONSTRUCT round-trip, but a mistyped variable now gives a hole where it used to drop the triple. The same holds for SEQ(?unbound).
  5. A slot is a hole and not an unknown value (§4). The rest follows from this one.
  6. undef is case insensitive in Turtle. This matches SPARQL, though true and false are case sensitive in Turtle.
